# 1. Назначение документа

Документ описывает пользовательские сценарии работы пользователей системы.

User Stories используются для:
* понимания потребностей пользователей;
* декомпозиции бизнес-требований;
* подготовки функциональных требований;
* формирования задач для разработки;
* подготовки критериев приемки.

Связанные документы:
* Business Requirements Document (BRD);
* Software Requirements Specification (SRS);
* API Contract (OpenAPI YAML);
* Postman Collection;
* Test Cases.

---


# 2. Общие правила написания User Stories
User Story должна отвечать на вопросы:

1. Кто пользователь?
2. Что он хочет сделать?
3. Зачем ему это нужно?

---


# 3. Формат User Story

Шаблон:

> Как [роль пользователя]

> я хочу [действие/возможность]

> чтобы [бизнес-ценность/цель]

## 4.1. Основные сценарии

## US-001 Регистрация пользователя (Создание учетной записи)
### User Story
- **Как** новый пользователь
- **я хочу** зарегистрироваться в системе
- **чтобы** получить доступ к функционалу платформы.

### Предусловия
Пользователь не имеет учетной записи.

### Основной сценарий (Happy Path)
1. Пользователь открывает страницу регистрации.
2. Пользователь вводит:
   - имя;
   - телефон;
   - email;
   - пароль.
3. Система проверяет корректность данных.
4. Система создает учетную запись.
5. Пользователь получает доступ к системе.

### Результат
Создан пользователь с ролью CLIENT.

### Acceptance Criteria
- Пользователь может успешно зарегистрироваться.
- Нельзя создать пользователя с занятым email.
- Пароль сохраняется безопасным способом.
- После регистрации пользователь автоматически авторизуется.

### Связь
- BR-001 (Регистрация и авторизация)
- FR-001 (Регистрация пользователя)
- FR-002 (Авторизация пользователя)

## US-002 Создание заявки через чат (Отправка текстового запроса)
### User Story
- **Как** клиент
- **я хочу** описать перевозку обычным текстом
- **чтобы** быстро создать заявку без ручного заполнения формы.

### Основной сценарий (Happy Path)
1. Клиент открывает чат.
2. Клиент вводит сообщение.

Пример:
> "Нужно перевезти 500 кг оборудования из Москвы в Санкт-Петербург завтра"

3. AI-ассистент анализирует сообщение.
4. Система определяет параметры:
   - город отправления;
   - город назначения;
   - тип груза;
   - вес;
   - дату отправки.
5. Создается заявка.

### Результат
Создана заявка со статусом CREATED.

### Acceptance Criteria
- Система принимает текстовый запрос.
- Система извлекает доступные параметры.
- Недостающие параметры запрашиваются у пользователя.
- Заявка сохраняется в системе.

### Связь
- BR-002 (Чат для заявки)
- BR-003 (Определение параметров)
- FR-003 (Создание заявки через AI-чат)
- FR-005 (Извлечение параметров перевозки)
- AI-001 (Анализ пользовательского сообщения)
- AI-002 (Извлечение параметров перевозки)

## US-003 Уточнение данных заявки (Ответ на уточняющие вопросы)
### User Story
- **Как** клиент
- **я хочу** получить уточняющие вопросы
- **чтобы** система могла правильно рассчитать перевозку.

1. Клиент отправляет заявку.
2. Система обнаруживает отсутствие обязательных данных.
3. Система задает вопрос.

Пример:
> "Укажите вес груза"

4. Клиент предоставляет информацию.
5. Система обновляет заявку.

### Обязательные параметры
- город отправления;
- город назначения;
- вес груза;
- тип груза.

### Acceptance Criteria
- Система запрашивает только отсутствующие параметры.
- Вопросы формулируются понятно на русском языке.
- После получения ответа система продолжает обработку заявки.
- Диалог не прерывается.

## US-007 Оплата заказа (Проведение оплаты через платежный шлюз)
### User Story
- **Как** клиент
- **я хочу** оплатить заказ
- **чтобы** подтвердить перевозку.

### Предусловия
- Заказ создан со статусом CREATED.
- Пользователь авторизован в системе.

### Основной сценарий (Happy Path)
1. Клиент открывает страницу оплаты заказа.
2. Система отправляет запрос платежному сервису.
3. Клиент выполняет оплату через платежный шлюз.
4. Платеж подтверждается.
5. Статус оплаты меняется на PAID.
6. Статус заказа обновляется на PAID.

### Статусы платежа
| Статус | Описание |
|--------|----------|
| PENDING | Ожидание оплаты |
| PAID | Оплачено |
| FAILED | Ошибка оплаты |
| REFUNDED | Возврат средств |

### Acceptance Criteria
- Статусы платежа соответствуют бизнес-правилам.
- После успешной оплаты статус заказа меняется с CREATED на PAID.
- Пользователь получает уведомление о результате оплаты.
- При ошибке оплаты пользователь видит понятное сообщение.

### Связь
- BR-012 (Обработка оплаты)
- FR-014 (Оплата заказа)
- INT-001 (Платежный сервис)

## US-008 Просмотр статуса заказа (Отслеживание состояния заказа)
### User Story
- **Как** клиент
- **я хочу** видеть статус заказа
- **чтобы** понимать этап перевозки.

### Основной сценарий (Happy Path)
1. Клиент открывает раздел "Мои заказы".
2. Система отображает список заказов с текущими статусами.
3. Клиент может открыть детальную информацию по каждому заказу.

### Возможные статусы
| Статус | Описание |
|--------|----------|
| CREATED | Заказ создан, ожидает оплаты |
| PAID | Заказ оплачен |
| ASSIGNED | Назначен перевозчик |
| IN_TRANSIT | Груз в пути |
| DELIVERED | Доставлен |
| CANCELLED | Отменен |
| EXPIRED | Время оплаты истекло |

### Отображаемая информация
- номер заказа;
- текущий статус;
- перевозчик;
- ожидаемая дата доставки;
- фактическая дата доставки (при наличии).

### Acceptance Criteria
- Пользователь видит актуальный статус заказа.
- Статус обновляется автоматически при изменении.
- Для каждого статуса отображается понятное описание на русском языке.
- История изменений статуса доступна для просмотра.

### Связь
- BR-010 (История заказов)
- FR-011 (История заказов)

## US-011 Ошибка распознавания параметров (Нераспознанный запрос)
### User Story
- **Как** клиент
- **я хочу** получить понятное сообщение об ошибке
- **чтобы** понять, что делать дальше.

### Основной сценарий (Happy Path)
1. Клиент пишет сообщение в чат, например: "Хочу перевезти груз".
2. AI не может определить обязательные параметры.
3. Система выводит сообщение:
   > "Не удалось определить город отправления и назначения. Укажите, пожалуйста, откуда и куда нужно перевезти груз."
4. Клиент уточняет данные.
5. Система продолжает обработку заявки.

### Acceptance Criteria
- Система всегда предоставляет конкретную информацию о том, какой параметр не распознан.
- Сообщение об ошибке содержит инструкцию по исправлению ситуации.
- Пользователь может продолжить диалог и уточнить недостающие данные.
- Диалог не прерывается, система ожидает уточнения от пользователя.

### Альтернативный сценарий (полное отсутствие параметров)
1. Клиент пишет: "Привет".
2. Система не может определить ни один параметр.
3. Система выводит сообщение:
   > "Здравствуйте! Для оформления перевозки мне нужно знать:
   > - Откуда нужно перевезти груз?
   > - Куда нужно перевезти груз?
   > - Какой вес груза?
   > - Какой тип груза?"
4. Клиент предоставляет все данные.
5. Система продолжает обработку.

### Связь
- BR-013 (Обработка ошибок и исключений)
- FR-015 (Обработка ошибок и исключительных ситуаций)
- AI-006 (Обработка нераспознанного запроса)

## US-012 Отсутствие тарифов (Нет доступных перевозчиков)
### User Story
- **Как** клиент
- **я хочу** получить сообщение, что тарифов нет
- **чтобы** скорректировать запрос.

### Основной сценарий (Happy Path)
1. Клиент указал параметры перевозки: Москва → Владивосток, 10 тонн, завтра.
2. Система выполнила поиск подходящих тарифов.
3. Подходящие тарифы не найдены.
4. Система выводит сообщение:
   > "К сожалению, по вашему маршруту нет доступных перевозчиков. Попробуйте изменить дату или вес груза."
5. Клиент может:
   - изменить параметры и повторить поиск;
   - обратиться к менеджеру для ручного подбора.

### Acceptance Criteria
- Система всегда информирует пользователя об отсутствии результатов.
- Сообщение содержит рекомендации по изменению параметров.
- Пользователь может вернуться к редактированию заявки.
- Система не создает заказ при отсутствии тарифов.

### Связь
- BR-013 (Обработка ошибок и исключений)
- FR-015 (Обработка ошибок и исключительных ситуаций)

## US-013 Отмена заказа клиентом (Отмена заказа до и после оплаты)
### User Story
- **Как** клиент
- **я хочу** отменить заказ
- **чтобы** не оплачивать ненужную перевозку.

### Основной сценарий (Happy Path)
1. Клиент открывает страницу заказа.
2. Нажимает кнопку "Отменить заказ".
3. Система запрашивает подтверждение:
   > "Вы действительно хотите отменить заказ №12345?"
4. Клиент подтверждает отмену.
5. Система проверяет возможность отмены.
6. Статус заказа меняется на CANCELLED.
7. Система отображает подтверждение:
   > "Заказ №12345 успешно отменен."

### Бизнес-правила отмены
| Статус заказа | Возможность отмены | Действие системы |
|---------------|-------------------|------------------|
| CREATED | Да | Отмена без последствий |
| PAID | Да | Отмена + инициирование возврата средств |
| ASSIGNED | Только по запросу в поддержку | Требуется ручное вмешательство |
| IN_TRANSIT | Нет | Отмена невозможна |
| DELIVERED | Нет | Заказ завершен |

### Acceptance Criteria
- Отмена возможна только для заказов со статусом CREATED или PAID.
- При отмене оплаченного заказа автоматически инициируется возврат средств.
- Пользователь получает уведомление об успешной отмене.
- Отмененный заказ сохраняется в истории с соответствующим статусом.

### Связь
- BR-013 (Обработка ошибок и исключений)
- FR-015 (Обработка ошибок и исключительных ситуаций)
- BRULE-006 (Время ожидания оплаты)
- BRULE-007 (Отмена оплаченного заказа)

## US-014 Возврат средств (Автоматический возврат при отмене оплаченного заказа)
### User Story
- **Как** клиент
- **я хочу** получить возврат
если заказ отменен после оплаты.

### Основной сценарий (Happy Path)
1. Клиент отменяет оплаченный заказ (статус PAID).
2. Система автоматически инициирует возврат средств через платежный шлюз.
3. Платежный сервис обрабатывает возврат.
4. Статус платежа меняется на REFUNDED.
5. Статус заказа меняется на CANCELLED.
6. Клиент получает уведомление:
   > "Средства по заказу №12345 возвращены. Ожидайте поступления на вашу карту в течение 3-5 рабочих дней."

### Acceptance Criteria
- Возврат инициируется автоматически при отмене оплаченного заказа.
- Статус платежа обновляется на REFUNDED.
- Пользователь получает уведомление о возврате.
- В истории заказа отображается информация о возврате.
- Сумма возврата равна сумме оплаты (полный возврат).

### Альтернативный сценарий (ошибка возврата)
1. Платежный сервис не может обработать возврат.
2. Система фиксирует ошибку.
3. Статус платежа остается PAID.
4. Система уведомляет администратора о проблеме.
5. Пользователь получает сообщение:
   > "Произошла ошибка при обработке возврата. Наш менеджер свяжется с вами в ближайшее время."

### Acceptance Criteria
- При ошибке возврата система уведомляет администратора.
- Пользователь получает понятное сообщение об ошибке.
- Данные о попытке возврата сохраняются в системе.

### Связь
- BR-013 (Обработка ошибок и исключений)
- FR-015 (Обработка ошибок и исключительных ситуаций)
- FR-014 (Оплата заказа)
- INT-001 (Платежный сервис)
- BRULE-008 (Возврат средств)

## US-015 Истечение времени оплаты (Автоматическая отмена просроченного заказа)
### User Story
- **Как** клиент
- **я хочу**, чтобы неоплаченные заказы автоматически отменялись
- **чтобы** не создавать лишних обязательств.

### Основной сценарий (Happy Path)
1. Клиент создал заказ со статусом CREATED.
2. Система запускает таймер оплаты (2 часа).
3. Клиент не оплачивает заказ в течение 2 часов.
4. Система автоматически меняет статус заказа на EXPIRED.
5. Заказ удаляется из активных.
6. Клиент получает уведомление:
   > "Время оплаты заказа №12345 истекло. Заказ автоматически отменен."

### Acceptance Criteria
- Таймер оплаты запускается автоматически при создании заказа.
- Время ожидания оплаты — 2 часа.
- По истечении времени статус заказа меняется на EXPIRED.
- Пользователь получает уведомление об истечении времени оплаты.
- Заказ сохраняется в истории со статусом EXPIRED.

### Связь
- BR-013 (Обработка ошибок и исключений)
- FR-015 (Обработка ошибок и исключительных ситуаций)
- BRULE-006 (Время ожидания оплаты)

# 7. Связь User Stories с другими документами

```
1. BRD (Бизнес-требования)
   │
   │  Определяет: цели, проблемы, бизнес-эффект, Scope.
   ▼

2. Business Requirements (Раздел 8 BRD)
   │
   │  Определяет: что должна делать система на высоком уровне.
   ▼

3. User Stories
   │
   │  Определяет: сценарии использования глазами пользователя.
   ▼

4. SRS (Функциональные спецификации)
   │
   │  Определяет: алгоритмы, бизнес-логику, правила расчета.
   ▼

5. API Contract (OpenAPI YAML / Swagger)
   │
   │  Определяет: эндпоинты, методы, JSON-схемы, коды ошибок.
   ▼

6. OpenAPI YAML → Postman Collection → Mock-сервер
   │
   │  Из одного OpenAPI файла получаем:
   │  - Документацию (Swagger UI)
   │  - Postman Collection для ручного тестирования
   │  - Mock-сервер для фронтенда
   ▼

7. Test Cases (Тест-кейсы)
   │
   │  Пишутся на основе OpenAPI + User Stories.
   ▼

8. Автоматизация тестов (Newman / RestAssured)
   │
   │  Запускаются в CI/CD при каждом коммите.
```
